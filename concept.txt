                    LOAD TESTING API - PROJECT CONCEPTS & OVERVIEW

1. WHAT IS A LOAD TESTING API?
--------------------------------------------------------------------------------
Load Testing is the process of putting simulated demand (traffic/users) on a 
software system, server, or API to measure its response time, stability, 
and reliability under normal and peak operating conditions.

A Load Testing API allows software systems, developers, and businesses to:
  - Programmatically launch high-concurrency traffic against target servers.
  - Measure performance metrics like Requests Per Second (RPS) and Latency percentiles 
    (p50, p90, p95, p99).
  - Automate performance verification in software deployment pipelines.

Real-World Analogy:
  Before opening a new bridge to the public, engineers drive heavy trucks onto 
  it to verify how much weight it can hold before it cracks or collapses.
  Load testing does the exact same thing for websites and API backends.


2. REAL-WORLD BUSINESS APPLICATIONS & USE CASES
--------------------------------------------------------------------------------
A. Black Friday / High-Traffic Launch Preparation:
   - Problem: E-commerce sites lose massive revenue if checkout crashes during peak sales.
   - Solution: Using our API, businesses simulate 50,000 shoppers hitting checkout 
     simultaneously BEFORE the event to catch database bottlenecks and memory leaks early.

B. Continuous Integration / Automated CI/CD Testing:
   - Problem: Developers accidentally push code updates that slow down API endpoints by 4x.
   - Solution: Every code update triggers an automated call to our Load Testing API. 
     If latency exceeds SLA thresholds (e.g. p95 > 250ms), the build automatically fails.

C. SLA (Service Level Agreement) Compliance & Benchmarking:
   - Problem: Enterprise SaaS contracts require proving 99.9% uptime and low latency.
   - Solution: Companies use our API to generate official performance reports for enterprise clients.


3. KEY BUSINESS BENEFITS
--------------------------------------------------------------------------------
1. Revenue Protection: Prevents server outages during high-stakes sales events.
2. Brand Protection: Keeps apps fast, preventing user frustration and churn.
3. Cost Optimization: Identifies exact server hardware limits so companies do not 
   overspend on unnecessary cloud infrastructure.


4. PROJECT TECHNICAL ARCHITECTURE OVERVIEW (PYTHON)
--------------------------------------------------------------------------------
- Core Framework: FastAPI (Async, high-performance web framework).
- Async Load Generation Engine: httpx + asyncio + uvloop for non-blocking 
  high-concurrency Virtual User (VU) simulation.
- Task Queue & Workers: Redis + ARQ (or Celery) for background job processing.
- Persistence: SQLAlchemy + SQLite/PostgreSQL for saving test runs and reports.
- Real-Time Telemetry: WebSockets / Server-Sent Events for streaming live metrics.
- Metrics Engine: Numpy / Percentile algorithms for accurate latency tracking (p50..p99).


5. ROADMAP PHASES
--------------------------------------------------------------------------------
- Phase 1: Single-Node Async Load Generation Engine & Core REST API endpoints.
- Phase 2: Background Task Worker Queue, Persistence DB, and WebSocket Live Ticks.
- Phase 3: SLA Assertion Engine, Webhook notifications, and HTML/JSON Report exports.


6. PYDANTIC DATA VALIDATION & BOUNDARIES (ge / le)
--------------------------------------------------------------------------------
To protect our system and ensure clean inputs, we use Pydantic Field validation:
  - 'ge' = Greater than or Equal to (>=)
  - 'le' = Less than or Equal to (<=)

Examples:
  - virtual_users: Field(ge=1, le=5000)
    Ensures at least 1 virtual user is specified, and caps traffic at 5,000 VUs 
    to prevent hardware resource exhaustion.
  - duration_seconds: Field(ge=1, le=3600)
    Ensures test duration is between 1 second and 1 hour (3,600s).

Benefits:
  - Automatically catches invalid client inputs and returns HTTP 422 errors 
    BEFORE executing backend load testing logic.
